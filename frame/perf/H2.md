# H2 (2026-10-13 11:12, second headset session): what the owner saw, and lane G's fixes

Session `$KARTFRAME_HOME/sessions/20261013-111257`, build `native` 0441316: 120 Hz, pipelined, 119.7
sets/s, 0.4 % late, 0.7 % repeats, compositor reused 0.2 %, GPU 3.5 ms menus / 5.9 ms race a set.
The owner: (1) "when moving my head every image was doubled" (head still: fine), (2) "the HUD wasn't
present and would flicker in only", (3) "the pointer and controller models didn't render when it was a
2D screen". All runs below: mock runtime, real Turnip GPU, 1728 per eye, 120 Hz, TU_DEBUG=sysmem.

## 1. Doubled images

- Image/pose pairing is clean. New exact check: with `MOCK_XR_STAMP=1` the game stamps every eye image
  with the display time its set was located for (and the eye); the mock reads the stamp back from the
  image each projection layer submits and compares it with the locate of the layer's poses. Pipelined
  and inline, with and without 2 ms prediction jitter, menus and race: 10 064 to 14 318 eye images a
  run, every one rendered for the locate of its submitted poses, none with the other eye's stamp.
- Display times: on SteamVR a pipelined set is located for "this prediction + one period", which need
  not be the next cycle's prediction. Layers are now ended with the display time their poses were
  located for (kept increasing; a repeated layer keeps the cycle's time); `KARTFRAME_END_TIME=cycle`
  is the old way. Mock with `MOCK_XR_PREDICT_JITTER=2`: old 0 of 7155 fresh layers carried their
  poses' time, new 7157 of 7159. Whether SteamVR's predictions jitter is in the next session's log.
- The cause found: VR interpolation did not interpolate. A set's display time lies 2 to 3 refreshes
  after the newest game frame's boundary, and the weight `(display - boundary) / interval` was clamped
  to 1: in the pipelined race 98 % of sets showed the newest game frame whole (mock: 2 to 54 of ~1180
  sets per 10 s between two frames), so each game frame stayed on two refreshes, 60 Hz scenery on a
  120 Hz panel. Anything the eye follows (the road and walls streaming past when the head turns) shows
  twice. Head still and looking ahead, little moves across the view. `stereo::SceneClock` samples the
  scene at the display time minus a delay it learns (running mean of display minus boundary, minus
  half an interval): mock race now 87 to 94 % of sets between two frames, motion uniform (unit check:
  step error under 0.002 frames at 90 and 120 Hz, leads 16.7 to 33 ms). `KARTFRAME_SCENE_CLOCK=0` is
  the old rule. Cost: none (one subtraction a set); the scene is shown about half a game frame later
  than the old rule intended (and earlier than what it actually did, a whole frame held twice).

## 2. HUD missing or flickering

- Not the FOVs: the headset's "screen clip self-check -2.00000" is the check's "not run yet" value
  (menus, first race seconds); in the race it read 0.00000 on the real asymmetric FOVs too.
- Cause: lane E's clip block was written at `screen_clip_offset(uniformSize)`, but `uniformSize` is
  padded to the 64-byte dynamic-offset alignment while the shader's clip fields follow the WGSL
  struct's end. The shader read padding (stale bytes), discarded nearly every 2D draw on the virtual
  screen, and let one through now and then on leftover bytes.
- Found headless: `MOCK_XR_PRESS` scripted A presses take the mock into a real Grand Prix race (Luigi
  Circuit). With the owner's settings (hud_virtual_screen = true, hand_hud = false) the eyes had no HUD
  with the clip on or off (`KARTFRAME_HUD_CLIP=0` only blanks the CPU block); hud_virtual_screen =
  false showed it; removing the shader clip brought it back.
- Fix: `ShaderInfo::structSize` places the block on both sides; the block carries a marker without
  which the shader does not clip (a future layout slip shows the HUD unclipped, never hides it).
  `frame/perf/hudrace.sh NAME` runs the scripted race and writes eye PNGs: TIME, LAP, position and map
  are on the screen in both eyes (mock FOVs now asymmetric, -52/44/48/-52 deg, self-check 0.00000).
- `KARTFRAME_HUD_CLIP=0` is no longer needed as a wrapper default.

## 3. Controllers and pointer in menus

A menu set now also renders the room around the screen into a packed two-eye image (3456x1728): plain
background, the controller models, the laser pointers with their marks, the screen's area transparent.
It goes out as one projection layer with the set's poses under the screen's quad (plus the panel
quad). `KARTFRAME_MENU_ENV=over` puts it over the quad, alpha-blended (controllers in front of the
screen stay in front, if SteamVR keeps the layer order); `=0` turns it off. Mock, warm caches, menus
30-90 s: 120.5 sets/s, 0 late, GPU 2.60 / 2.99 ms a set (without: 1.25 / 5.89), encode 0.52 ms.
